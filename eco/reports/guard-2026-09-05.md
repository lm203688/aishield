### 2.1 ⚠️ 关键异常：部署链路静默停摆，线上代码落后 main 82 个提交

| 项 | 值 |
| --- | --- |

| 差距 | **落后 82 个提交，4 天**（GitHub compare API：`ahead_by=82, behind_by=0`） |

这 82 个提交里包含 09-01 之后所有新增的情报规则、radar 规则晋升与能力修复 —— **线上扫描器至今仍在用 09-01 的规则集对外提供服务**。

#### 根因：VPS 上的 `git fetch` 失败被 `|| true` 吞掉

`scripts/deploy-named-tunnel.sh:44-45`：

```bash
git fetch --all 2>/dev/null || true
git reset --hard origin/main 2>/dev/null || git pull origin main 2>/dev/null || true
```

`git fetch` 失败（stderr 被 `2>/dev/null` 丢弃，失败被 `|| true` 吞掉），接着 `git reset --hard origin/main` 把工作树重置到**本地那个早已陈旧的 `origin/main` 远端跟踪引用**。09-04T07:59 那次部署的日志即为铁证：

```
[13:00:07] HEAD: 93fcd10c -> 93fcd10c          ← fetch 完全没有推进
[13:00:07] commit 对比: 运行进程=68a497f5… / 磁盘=93fcd10c…
[13:00:07] 运行进程落后于磁盘代码（commit 不一致）-> 标记重启
[13:00:08] 强制重启 Python API 进程（当前commit=68a497f5… 目标=93fcd10c…）
```

脚本里那段「git 不可用时走 raw 兜底」的分支（`L97`）触发条件是 `after_head = "nogit"`，也就是**只有 git 整个不存在时才走**。现在 git 存在、只是 fetch 失败，于是兜底永不触发。

净效果：每天 pipeline 按时跑，把 API 重启到 09-01 的旧代码，然后报告成功。

#### 这不是新问题，但形变了

昨天（09-04）报告里的诊断是「CI 红灯挡住部署」。今天 CI 已经转绿（`AIShield CI/CD` 09-04T00:39 success、`Closed-Loop Spine` 09-04T07:56 全链路 success，`6. 部署` 与 `Post-Deploy Verification Gate` 双双 success）——**闸门让开了，但代码还是没上去**。说明昨天的红灯只是叠加在真正的病灶上的一层表象。

#### 门禁为什么绿：四条断言从不与 GitHub main 比对

`Post-Deploy Verification Gate` 的四条硬断言是：

1. 线上 `status == ok`
2. 线上 commit == **VPS 磁盘 commit**
3. 线上 `rules_count` == **VPS 磁盘** `disk_rules_count`
4. `deployed_at` 非空

09-04T08:00 的实际输出：

```
commit     : 线上=93fcd10c5a07cf882e7bfbb7a3ee6da122e3a19c  磁盘=93fcd10c
✅ 四项断言全部通过：线上与磁盘一致
```

断言 2 和 3 的参照物是 **VPS 磁盘**，而 VPS 磁盘本身就是那个 4 天没更新的陈旧副本 —— 磁盘越陈旧，线上与磁盘就越一致，断言就越绿。这是一个**自我循环验证**：门禁在结构上无法看见「磁盘自己落后了」，而恰恰是这一点决定了它永远不可能报红。

> 注：门禁里其实写了一段正确的自省（「不能退回读仓库里的旧文件…会把『看起来验证过了』当成『验证通过了』」），但它防的是「用 checkout 出来的旧文件冒充线上」，没有防到「参照物整体漂移」。
