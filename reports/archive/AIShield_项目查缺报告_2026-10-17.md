## 1. 文档体系缺口（最大缺口区，细节拉满）

  2. **docs 散落 5 条真缺**：`docs/index.md` 链接的 `aishield-trust-standard-v0.1.md`、`agent-computer-security-plane.md`、`agent-ecology-evolution-directions.md`、`partnership-strategy.md`、`how-to-submit-pr.md` **全部不存在**（可能是规划中从未落笔，或改名未同步）。

- **修复建议**：加一个 `scripts/check_doc_links.py` 作为 E 级门禁（参照已有 `validate_workflows.py`），CI 拦截新增断链；对 15 个悬空链接做“补写 or 去链”二选一。

### 1.2 AGENTS.md 自身事实错误（【确证】）

- **修复建议**：AGENTS.md 同步 npm 版本号到 4.11.0；把 `sync_readme_counts()` 改为正确的 `rule_count_gate.py --check`；这是“文档即契约”项目的自我讽刺，优先级 P0。

### 1.3 mcp-server/README.md 规则数漂移（【确证】违反不变量#3）

- 这正是不变量#3 想防却没防住的——根因见 §2（同步脚本名错 + 264 多处硬编码）。
- **修复建议**：规则数改为**单一计算源**（见 §2.4），所有文档用 `rule_count_gate.py` 输出渲染，删除所有手写数字。

### 1.4 英文文档 0 篇（【确证】）

## 2. 规则数真值与一致性（核心可信度地基）

### 2.1 规则数无单一真值源（【确证】漂移炸弹）
- 规则数 **≥4 处硬编码/半硬编码**：
  - `api/static/.well-known/agent.json:139` → `"total": 264`
  - `api/static/agent-discovery.json:15` → `"total": 264`
  - `api/ecosystem_request_bodies.py:117` → `"coverage": {"rules": 264}`
  - `mcp-server/README.md` 手写 264/235/291
- 规则实际是**数据驱动**：`scanner/rules.py`（2055 行）通过 `json.load`/`glob` 从 `data/` 下的 JSON 规则文件加载；`data/radar_rules.json` 的 `rules` 长度为 19（对应“雷达 19”）。真实总数由 `scripts/rule_count_gate.py` 计算。
- 问题：**计算源(rule_count_gate) 与 3 处手写副本 解耦**。一旦规则数变动，副本不会自动更新——这正是 **2026-10-05 “线上 235/241、本地 264、门禁报一致”事故**的同一根因。
- **修复建议**：删除所有手写规则数，文档/静态 JSON 全部由 `rule_count_gate.py` 在构建期注入（`--emit` 模式生成 agent.json 等）。让“真值”只有一个出口。

### 2.2 AGENTS.md 引用了不存在的脚本（【确证】）
- AGENTS.md:26 要求跑 `scripts/sync_readme_counts()`，但该文件不存在。真实脚本是 `scripts/rule_count_gate.py`（grep `scripts/` 确认存在，且 declaration_surface 注释里也提到它）。
- 后果：**“规则数同步”这个不变量没有任何可执行的自动化保障**，纯靠人手——必然再次漂移。
- **修复建议**：AGENTS.md 改名为 `rule_count_gate.py --check`；CI 加一步强制该门禁；顺带确认 `rule_count_gate.py` 是否真的覆盖了 api/static 那两份 JSON（见 §2.3 盲点）。

### 2.3 声明面门禁有盲点（【确证】事故同型未根治）
- `api/declaration_surface.py`（301 行）本身是**实质性模块**，注释详实记录了 2026-10-05 漂移事故的形状：
  - `server.py:483` Trust API 分支 `path=="/.well-known/agent-card.json"` **提前 return**，读 `docs/.well-known/agent-card.json`（真正在服务）
  - `server.py:768` 静态资产分支永远执行不到（先命中者胜）= **死代码**
  - `rule_count_gate` 覆盖的是后者（api/static 前缀），前者（docs/ 前缀）被 `_is_declared_surface` 当作“历史快照”**整体豁免** → 放行
- **盲点**：门禁豁免了 `docs/` 前缀，而该前缀恰好是**实际对外服务**的面。所以“一致性检查通过”不再构成证据。2026-10-05 事故的根因（验证面与服务面脱节）**只被诊断、未被结构性关闭**。
- **修复建议**：`_is_declared_surface` 不得豁免实际服务路径；加一条“服务出去的数字 == 计算源数字”的运行时断言（server 启动自检）。

### 2.4 264 数字本身的口径混乱（【确证】）
- mcp-server/README 给的分解 `113+62+11+22=208` 标成 235，再加 情报 8 + 雷达 19 = 235+27=262，又不是 264。三套口径（逐类 235 / 含情报雷达 264 / Skill 291）互相嵌套、无一处自洽。
- **修复建议**：在 `rule_count_gate.py` 输出一份带分类计数的 JSON（MCP 类 X / ASI 类 Y / 沙箱 Z / 中文 W / 情报 I / 雷达 R），文档与静态文件一律引用该 JSON，消灭手写分解。

## 3. 依赖与构建地基缺口

### 3.1 依赖声明实质性缺失（【确证】）
- `requirements.txt` 是**空文件**；无 `pyproject.toml`；`setup.py` 第 24 行 `install_requires=[]`（空）。
- 但 AGENTS.md 明确说“cryptography / pyyaml 是必需的，不是可选增强”，且 `render.yaml` 的 build 命令写 `pip install -e . 2>/dev/null; true`——**安装失败被刻意吞掉**。
- 后果链（已在地基报告实锤）：生产装不上 cryptography → 信任层静默降级 HMAC → “可公开验证”变“仅服务端自证”。
- **修复建议**：`setup.py` 的 `install_requires` 钉 `cryptography`、`pyyaml`、`requests`（仅生态/在线模块可选）；删除 render.yaml 的 `; true`；`requirements.txt` 改为指向 setup 或显式列出。

### 3.2 测试依赖未声明（【确证】）
- `tests/test_invariant_property.py:34` import 了 `hypothesis`，但**全仓无任何地方声明 hypothesis**（requirements/setup/pyproject/AGENTS quickstart 都没有）。按 AGENTS.md 命令（`pip install pytest cryptography pyyaml`）装完，pytest **收集阶段直接崩溃**。
- 这是“任何人 clone 后按 README 一条命令跑测试”承诺的硬违约。
- **修复建议**：把 hypothesis 加入 `requirements-dev.txt` 或 setup 的 `extras_require['test']`；AGENTS.md quickstart 同步。

### 3.3 E11 反模式复发：内联 pip install（【确证】）
- AGENTS.md 铁律#6 + E11 要求：凡跑入口的 job 必须先引用 `.github/actions/prepare-tests`（统一装依赖）。但仍有 **5 处 workflow 各自 `pip install`**：
  - `ci.yml`、`deploy-server.yml`（`pip install cryptography`）、`feature-closed-loop.yml`（`pip install pyyaml`）、`meta-monitor.yml`（`pip install pyyaml`）、`unified-security-scan.yml`（`pip install -e .` —— 而 setup.py 不装 cryptography）。
- AGENTS.md:48 自己承认“另外还有 3 个 job 属于同一类”。**门禁 E11 显然没拦住自己**。
- **修复建议**：E11 升级为“禁止 workflow 内出现 `pip install` 字面量（除 prepare-tests action 内）”，扫描失败时阻断。

## 6. 测试信号纯度缺口

### 6.1 实跑结果（【确证】隔离 venv，装齐 pytest/pyyaml/cryptography/hypothesis）
- **2245 通过 / 2 失败 / 2 错误 / 26 跳过**（耗时约 6 分钟）。**不是全绿**。
- 2 失败：来自 **CRLF**（`.github/workflows/rule-promoter.yml` 与 `.github/actions/prepare-tests/action.yml` 被项目自己的 E9 门禁抓到）—— 根因见 §8.1。
- 2 错误：`tests/e2e_test.py`、`tests/quick_test.py` 被 pytest 默认收集即抛错（疑似顶层 import 副作用 / 缺依赖），**门禁本身把这两个文件当普通测试收集了**。
- 26 跳过：多为环境/可选依赖跳过，需逐条确认非“永远跳过”。
